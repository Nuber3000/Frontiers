# План разработки Frontiers

## Цель первой версии

Два человека открывают браузер, входят в комнату по приглашению и играют полный
матч колодами Королевства Бургундия. Проект должен запускаться из GitHub на своём
Linux-сервере.

## Текущий режим работы

По последнему решению владельца игровая часть реализуется автономно. DevOps-часть
разбираем вместе, небольшими шагами с объяснением каждого файла и команды.
Публикация релизов и изменения сервера выполняются после согласования.

## Этапы

| Этап | Результат и критерий готовности | Состояние |
| --- | --- | --- |
| 0. Подготовка | GitHub, Python, окружение, структура и описание проекта | Готово |
| 1. Карта и сила | Обычный отряд, три линии, пример подсчёта | Готово |
| 2. Рука и поле | Выкладывание отряда и сохранение состояния при ошибке | Готово |
| 3. Движок матча | Подготовка колод, замена руки, очередность, пас, раунды, результат | Готово |
| 4. Первая CI-проверка | GitHub Actions запускает игровые тесты | Перенесено в совместный DevOps-этап |
| 5. Способности | Погода, особые карты, иммунитеты, синергии, выбор целей и превращения | Готово |
| 6. Бургундия | Авторская коллекция, две колоды, способность фракции и пять вариантов Франциска | Готово |
| 7. Сетевой сервер | Комнаты, сессии, серверные команды, персональные обновления и восстановление | Готово |
| 8. Интерфейс | Полный матч двух браузерных игроков, выбор целей, реванш и мобильная ширина | Проверено в браузере |
| 9. Контейнеризация | Воспроизводимые зависимости, Dockerfile, Compose и локальный контейнер | Следующий совместный этап |
| 10. Сборка и релиз | CI, тесты, сборка и публикация версионированного образа | Вместе с владельцем |
| 11. Linux-сервер | HTTPS, настройки, логи, проверка работоспособности, обновление и откат | Вместе с владельцем |

## Что уже проверяется

- Допустимые ходы и отсутствие изменений после отклонённых команд.
- Погода, порядок модификаторов, герои, лидер, Казнь и выбор целей.
- Добор, шпионы, Лекари, Чучело, Призыв, Берсерки и Наследие.
- Раунды, ничьи, пустая колода и завершение матча.
- Сохранность экземпляров карт на протяжении 100 разных полных матчей.
- Изоляция сессий, скрытие чужой руки и последовательная обработка команд.
- Реальная игра в двух браузерных сессиях, перезагрузка, реванш и пас до ничьей.

Точные договорённости теперь находятся в [правилах](rules.md); устройство программы
описано в [архитектуре](architecture.md).

## Как будем проходить DevOps-этап

1. Запустить готовую игру и разобраться, какие процессы и порты ей нужны.
2. Просмотреть текущие изменения и сохранить код в Git.
3. Выбрать способ фиксации зависимостей и объяснить воспроизводимость сборки.
4. Написать Dockerfile: базовый образ, установка пакета, непривилегированный
   пользователь, команда запуска, сигналы и проверка работоспособности.
5. Написать Compose и повторить локальный матч в контейнере.
6. Добавить GitHub Actions для автоматических тестов и сборки.
7. Настроить публикацию образа, теги и версию релиза.
8. Подготовить Linux-сервер, обратный прокси, HTTPS и конфигурацию окружения.
9. Выполнить развёртывание, собрать логи, проверить обновление и откат.

Для каждого шага сначала объясняем назначение, затем меняем один небольшой участок
и проверяем результат.

## Ограничения и дальнейшее развитие

Первая версия использует один процесс и хранит комнаты в памяти. Для сохранения
матчей после перезапуска или нескольких реплик позже понадобятся внешнее хранилище
и дополнительная синхронизация. PostgreSQL, миграции, резервное копирование,
метрики и инфраструктура как код будут следующими учебными задачами, когда
появятся соответствующие требования.

До оформленного публичного релиза нужно выбрать лицензию исходного кода.
