# Нагрузочная проверка Frontiers

Генератор: Grafana k6 2.3.0 через Docker Desktop на Windows или GitHub Actions.
Сценарий: `tests/load_game.js`. Устанавливать k6 на игровой сервер и менять
работающее приложение не требуется. Запуск основного сервера выполняет владелец
в выбранное время; сценарий сам не запускает запросы к публичному адресу.

## Что измеряем

Один VU (virtual user, виртуальный пользователь k6) управляет **одной комнатой
и двумя игроками** с отдельными cookie-сессиями и WebSocket-соединениями.
Поэтому ROOMS=5 означает 10 игроков, а не пять. Комнаты создаются постепенно
за RAMP_SECONDS (по умолчанию пять секунд). Каждый VU создаёт одну комнату за запуск.
После наращивания все комнаты продолжают играть ещё SECONDS до общего времени
остановки. Например, RAMP_SECONDS=60 и SECONDS=300 — примерно минута наращивания
и пять минут полной нагрузки, затем штатное завершение. Установление соединений
занимает дополнительное время: фактический интервал от подключения последней
комнаты до запланированной остановки выводится в отчёте.
Дополнительно работает один отдельный VU сценария `health`, который проверяет
`/healthz` примерно раз в пять секунд и не создаёт комнат. Поэтому k6 показывает
ROOMS + 1 виртуальных пользователей: например, для 20 комнат — 21 VU и 40
игровых WebSocket-соединений. Номера VU игровых комнат могут начинаться с 2.

Игроки выбирают готовые колоды разных фракций из каталога сервера, подтверждают
готовность, оставляют начальную руку и отправляют допустимые игровые действия.
Сценарий проверяет версии и подтверждение хода у обоих участников, обрабатывает
выборы лекарей, использует лидеров и пасует. После завершения матча начинается
реванш в той же комнате. Новые комнаты на каждый матч не создаются.

Задержка между ходами пары по умолчанию — 2 секунды. В пяти комнатах это примерно
2,5 игровых команды в секунду плюс начальные HTTP-запросы и heartbeat.
Встроенный лимит приложения 180 команд за 10 секунд на игрока не отключается.

Проверяются HTTP API и живые WebSocket-соединения. Изображения, DOM, анимации,
FPS браузера и одновременная загрузка всех иллюстраций этим сценарием не измеряются.
Это отдельная проверка сервера игры, а не эмуляция полного браузера.

## До запуска

Договоритесь, чтобы во время первого теста друзья не играли: используется основной
экземпляр, и нагрузка может увеличить задержки общих ресурсов. Генератор работает
на другом компьютере, чтобы не отнимать CPU и память у игрового сервера.

В SSH-терминале на сервере:

```bash
cd /opt/frontiers
nproc
free -h
df -h /
sudo docker compose ps
sudo docker compose stats app
```

Зафиксируйте характеристики и расход памяти до теста. В `stats` наблюдайте CPU,
память, сеть и Block I/O. Во втором SSH-терминале можно открыть `vmstat 1`:
проверьте загрузку CPU, очередь процессов, swap и ожидание диска. Во время нагрузки
не собирайте образ, не очищайте Docker и не перезапускайте приложение.

## Первый запуск с Windows: 5 комнат, 60 секунд

Запустите Docker Desktop. В PowerShell, из корня локального проекта:

```powershell
cd D:\Projects\Frontiers
New-Item -ItemType Directory -Force artifacts\load | Out-Null
docker pull grafana/k6:2.3.0
```

Следующая команда **начинает тест основного сервера**. Выполните её в выбранное окно:

```powershell
docker run --rm -it --mount "type=bind,src=D:\Projects\Frontiers\tests\load_game.js,dst=/scripts/load_game.js,readonly" --mount "type=bind,src=D:\Projects\Frontiers\artifacts\load,dst=/results" grafana/k6:2.3.0 run -e BASE_URL=http://144.31.199.213:443 -e ROOMS=5 -e SECONDS=60 -e THINK_MS=2000 -e REPORT=/results/rooms-5.json /scripts/load_game.js
```

Это HTTP на порту 443, поэтому протокол оставлен `http`, как у текущей игры.
Сценарий требует явного BASE_URL, запрещает перенаправления и не содержит
публичного адреса по умолчанию. Для локальной проверки из Docker Desktop
используйте `http://host.docker.internal:8000`, если игра запущена на Windows.

Отчёт появится в `artifacts/load/rooms-5.json`; каталог исключён из Git. Отчёт
не содержит cookie и скрытых рук. В консоли будут коды только созданных тестовых
комнат и итоговые метрики. Никакие чужие комнаты сценарий не использует.

## Запуск из GitHub Actions

Workflow `.github/workflows/load-test.yml` запускает тот же сценарий с отдельной
машины GitHub. Это помогает сравнить результат с Windows через Wi-Fi и VPN.
Другой источник нагрузки меняет сетевой маршрут: удачный тест не доказывает
отсутствие всех ошибок сервера, но помогает отделить их от проблем пути клиента.

Изменения сценария и workflow готовятся в ветке `test/load-testing` и проходят
Pull Request в `main`. Тесты остаются в репозитории вместе с приложением.
Чтобы GitHub показал кнопку ручного запуска нового workflow, его файл сначала
должен присутствовать в основной ветке.

После объединения Pull Request:

1. Откройте **Actions → Load test (manual) → Run workflow**.
2. Выберите `main`, введите `http://144.31.199.213:443` без завершающего `/`.
3. Для первого прогона выберите **5** комнат, удержание **60** секунд,
   наращивание **5** секунд и паузу между ходами **2000** мс.
4. В выбранное время нажмите **Run workflow** и наблюдайте ресурсы сервера
   в SSH-терминале. После успешного отчёта отдельно запускайте 20 комнат на 300
   секунд; следующая ступень автоматически не стартует.
5. В завершённом запуске скачайте **Artifacts → load-test-…**. В архиве находятся
   `summary.json`, `console.txt`, параметры и время начала UTC. При провале порогов
   запуск будет красным, а доступные отчёты всё равно загрузятся.

Только `workflow_dispatch`: push, Pull Request и расписание нагрузку не запускают.
Адрес вводится при каждом запуске, публичного адреса по умолчанию у workflow нет.
Одновременно выполняется не больше одного запуска этого workflow; следующий
ожидает в очереди. Отложенный запуск тоже нужно отменить, если выбранное окно
нагрузки уже закончилось.

Остановка — **Cancel workflow** на странице запуска. При принудительной отмене
финальный JSON и штатное завершение тестовых комнат не гарантируются.
Обычные журналы GitHub помогут, даже если архив не успел загрузиться.

Этот workflow не обновляет сервер и не меняет настройки приложения. Существующий
CI может запускать проверки на Pull Request и собирать/публиковать образ после
объединения в `main`; нагрузочный workflow от него независим.

## Метрики и остановка

- `frontiers_actor_ms`: время от отправки команды до получения нового состояния
  отправившим её игроком.
- `frontiers_both_players_ms`: время до получения нового состояния обоими игроками.
  Включает сеть между генератором и сервером, обработку команды и рассылку.
- p50 — медиана; p95 — 95% измерений не медленнее этого значения; p99 — 99%.
- `frontiers_commands`: команды, подтверждённые обоими участниками.
- `frontiers_connected_rooms`: комнаты, у которых открылись оба игровых сокета.
  Должно совпасть с ROOMS. Созданная комната ещё не означает двух подключённых игроков.
- `frontiers_room_connected_at_ms`: время подключения второго игрока комнаты
  относительно начала сценария, включая наращивание нагрузки.
  Последняя комната должна подключиться достаточно рано, чтобы до общей остановки
  оставалось хотя бы 90% заданного времени удержания. Иначе тест не выполнит
  заявленный профиль нагрузки и будет отмечен как неуспешный.
- `frontiers_capacity_rejections`: ответы 503 «Сервер заполнен» при создании комнат.
  Это достижение ограничения числа комнат, а не доказательство перегрузки CPU.
- `frontiers_clean_rooms`: тестовые комнаты, в которых оба участника подтвердили
  завершённый матч перед закрытием соединений. Должно совпасть с ROOMS; это не
  удаление комнаты из памяти сервера.
- `frontiers_matches`: партии, завершённые игровым сценарием; служебная сдача
  при остановке сюда не включается.
- `frontiers_errors`: ошибки протокола, неожиданные закрытия или отсутствие
  подтверждения игровой команды за пять секунд.
- `frontiers_health_errors`: неуспешные пробы `/healthz`, включая тайм-ауты.
  Это отдельная метрика; `http_req_failed` учитывает ошибки всех HTTP-сценариев.

Начальные критерии: ошибок приложения нет, HTTP-ошибок меньше 1%, p95 рассылки
обоим игрокам меньше 1000 мс, p95 `/healthz` меньше 500 мс. Это выбранные для
первой проверки ориентиры, а не обещанная производительность сервера.
Ошибки приложения или HTTP могут автоматически прервать тест после первых
15 секунд. Нарушение порога задержки отмечается в отчёте и коде завершения k6.
`/healthz` опрашивается отдельным VU примерно раз в пять секунд.
Провал такой пробы сохраняется в отчёте и делает итоговый тест неуспешным,
но не закрывает игровую комнату сам по себе. Общие правила аварийной остановки
при доле HTTP-ошибок от 1% и игровых ошибках сохраняются.
Синхронный HTTP-запрос в пробе не блокирует WebSocket-обработчики игровых VU.

В первой версии сценария пробы выполнялись синхронно внутри первого игрового VU.
Это могло завышать его задержки и мешать завершению этой комнаты при тайм-ауте.
Отчёты той версии нужно интерпретировать с этим ограничением; сравнение новых
результатов со старыми не является полностью одинаковым профилем нагрузки.

Ручная остановка — **Ctrl+C в PowerShell генератора**. Остановите тест, если
игра становится недоступной, задержки растут до секунд, процесс упирается в CPU,
начинается устойчивый swap или память приближается к лимиту. Контейнер приложения
для остановки генератора перезапускать не нужно.

При штатном окончании сценарий сдаётся в собственной незавершённой партии,
дожидается подтверждения и закрывает оба сокета. При аварии или принудительном
прерывании это не гарантируется — в консоли остаются коды тестовых комнат.

## Следующие ступени

При обрыве сценарий печатает исходный `event.error` k6, время UTC и строку
`DIAGNOSTIC`: номер игрока, состояние сокетов, версии игры, давность последнего
сообщения и ожидающую команду. Cookie, содержимое рук и тексты WebSocket-пакетов
не записываются. Медленные HTTP-запросы дольше секунды отмечаются отдельно.
Пороги и автоматическая остановка при этом не меняются.

Для диагностического прогона сохраните весь вывод команды Docker в PowerShell,
передав k6 `--log-output=stdout` перед `run` и добавив в конец команды:

```powershell
2>&1 | Tee-Object -FilePath artifacts\load\rooms-20-diagnostic.console.txt
```

Вывод в stdout предотвращает оформление обычных строк k6 из stderr как
`NativeCommandError` в Windows PowerShell. Реальные ошибки остаются в выводе
и отчёте. Например: `grafana/k6:2.3.0 --log-output=stdout run --quiet ...`.

Первичная ошибка может находиться выше массовых закрытий при остановке k6.
Время UTC из журнала сопоставляется с `docker compose logs --timestamps`.
Фрагмент access-лога с ответами 200 не исключает рестарт или ошибки в другом
участке журнала. После обрыва сначала проверьте логи, перезапуски и OOM, затем
согласуйте повтор; не увеличивайте нагрузку автоматически.

После первого отчёта и восстановления обычных метрик можно повторить команду,
изменив ROOMS, SECONDS, RAMP_SECONDS и имя REPORT:

| Комнат | Игроков / сокетов | Наращивание | Удержание | Пауза между ходами |
| --- | --- | --- | --- | --- |
| 5 | 10 | 5 секунд | 60 секунд | 2000 мс |
| 10 | 20 | 5 секунд | 180 секунд | 2000 мс |
| 20 | 40 | 5 секунд | 300 секунд | 2000 мс |
| 40 | 80 | 30 секунд | 300 секунд | 2000 мс |
| 64 | 128 | 30 секунд | 300 секунд | 2000 мс |
| 96 | 192 | 60 секунд | 300 секунд | 2000 мс |
| 128 | 256 | 60 секунд | 300 секунд | 2000 мс |

Не запускайте ступени одновременно. Сначала оцените предыдущий отчёт. Данные
локальной проверки самого сценария не показывают ёмкость арендованного сервера.

У приложения максимум 128 комнат по умолчанию. **Завершённые и ожидающие комнаты
тоже занимают места**. После обновления приложения они автоматически удаляются,
когда оба игрока отключены не менее 120 секунд; фоновый обход идёт каждые 10 секунд.
Это относится и к прерванным активным матчам. Между прогонами дождитесь закрытия
соединений и ещё примерно 130 секунд при настройках по умолчанию. При сетевой
аварии сервер может обнаружить обрыв не сразу. Открытая вкладка комнаты сохраняет
её, поэтому закройте тестовые вкладки. Ступени создают новые комнаты и без паузы
могут заполнить лимит оставшимися от предыдущих прогонов комнатами.
HTTP 503 «Сервер заполнен» может означать достижение этого лимита, а не нехватку
CPU. Не повышайте лимит и не перезапускайте основную игру ради очистки без
отдельного решения. Для дальнейшего поиска предела удобнее отдельный экземпляр.

Для теста 128 комнат нужны **128 свободных мест**. Даже одна существующая комната
помешает достичь цели при текущем лимите. Сценарий не удаляет чужие комнаты,
не повышает лимит и не перезапускает приложение. При отказе в создании он
явно указывает причину, сохраняет ошибку и считает прогон неуспешным. Число 128
взято из FRONTIERS_MAX_ROOMS по умолчанию: это ограничение конфигурации,
а не измеренная максимальная производительность сервера.

Очистка на 120 секунд — изменение серверного приложения: одного обновления k6
недостаточно, нужен деплой нового образа. У прежней версии сроки хранения были
один час для лобби и завершённых матчей и сутки для брошенных активных матчей.
При настройке FRONTIERS_DISCONNECTED_ROOM_TTL учитывайте новый срок между тестами.

После успешных 128 комнат с паузой 2000 мс можно отдельно проверить 1000, 500
и 250 мс. Эти варианты доступны в GitHub Actions вместе с удержанием до 600
секунд. Для Windows параметры те же: `-e ROOMS=128 -e SECONDS=300
-e RAMP_SECONDS=60 -e THINK_MS=2000` (в одной команде).
Сначала меняйте только один параметр и анализируйте предыдущий результат.
Не увеличивайте одновременно число комнат и скорость ходов.

В 128 комнатах с паузой 2000 мс верхняя оценка — 64 команды/с; при 250 мс —
512 команд/с. Фактический поток ниже: каждая пара ждёт подтверждения команды
от обоих игроков и только затем выдерживает паузу. Это модель фиксированного
числа игроков, а не гарантия заданного числа запросов в секунду. Сам генератор
тоже может стать ограничением; сравнивайте его показатели и ресурсы сервера.

Общий момент остановки отличается от старого сценария, где каждая комната жила
SECONDS после собственного подключения. При длинном наращивании ранние комнаты
теперь работают дольше, чтобы дождаться остальных. Для сравнения сохраняйте
параметры и версию сценария; точные границы профиля важны для интерпретации p95.
