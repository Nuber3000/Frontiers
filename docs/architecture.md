# Устройство игровой версии

```text
Браузер (HTML / CSS / JavaScript)
  ├─ HTTP: каталог, создание комнаты, вход, готовность
  └─ WebSocket: команды игрока и персональные снимки состояния
        ↓
  app.py → rooms.py → engine.py
                       ├─ models.py — состояние матча
                       └─ catalog.py — определения карт и колод
```

## Файлы

| Файл | Ответственность |
| --- | --- |
| `models.py` | Описание карты, экземпляр с уникальным ID, карта на поле, состояние игрока |
| `catalog.py` | Авторская коллекция, пять лидеров, готовые колоды и проверка состава |
| `engine.py` | Допустимые действия, эффекты, пересчёт силы, раунды, персональный вид |
| `rooms.py` | Места игроков, комнаты, последовательная обработка, время хранения |
| `app.py` | HTTP/WebSocket, cookie, проверка входных данных и раздача интерфейса |
| `__main__.py` | Параметры локального запуска Uvicorn |
| `static/` | Браузерный интерфейс без внешних CDN и сборщика |
| `tests/test_engine.py` | Контракты правил и полные симулированные матчи |
| `tests/test_api.py` | Сессии, сетевой протокол и конкурентные команды |
| `tests/browser_smoke.py` | Два браузерных игрока, полный матч, возврат и реванш |

`cards.py`, `player.py` и два простых скрипта в `examples/` сохранены как первые
учебные примеры. Полноценный матч использует экземпляры карт из `models.py`:
каждая копия обладает собственным случайным ID, а выложенная карта — выбранным рядом.

## Атомарность действия

Команда включает ожидаемую `version`. Движок проверяет её, делает копию матча и
применяет действие к этой копии. Успех возвращает новое состояние с увеличенной
версией; ошибка оставляет исходное состояние нетронутым.

В комнате команды проходят через `asyncio.Lock`. Две команды с одной версией не
могут обе успешно изменить матч. Сервер проверяет очередь, наличие карты, ряд,
цель и доступность способности независимо от интерфейса.

Пример команды по WebSocket:

```json
{"type":"play","card_id":"случайный ID экземпляра","row":"ranged","version":7}
```

Ответ с обновлением:

```json
{"type":"state","state":{"code":"КОДКОМНАТЫ","me":0,"revision":12,"seats":[],"game":{}}}
```

Содержимое `game` в примере опущено. В настоящем ответе находятся игроки, поле,
счёт, погода, события и разрешённые действия. Игрок видит только свою руку и число
карт в чужой руке; порядок обеих колод не передаётся. Ошибка имеет тип `error` и
сообщение. При устаревшей команде ответ также содержит актуальный персональный снимок.

## Сессии и восстановление

Место игрока связано с HttpOnly cookie со случайным токеном. В памяти комнаты
хранится его SHA-256, а не исходный токен. Сам код приглашения позволяет занять
свободное место, но не читать чужой матч. Повторный вход с той же cookie возвращает
тот же слот. Токены не передаются в ссылке и не записываются в журналы игры.

Браузер восстанавливает WebSocket после сетевого разрыва и получает полный
снимок. Перезагрузка страницы использует сохранённый код комнаты и ту же cookie.
Сохранение состояния на диск пока отсутствует.

Запросы браузера с чужим Origin отклоняются; входные команды проверяются Pydantic.
WebSocket ограничивает размер сообщения, частоту команд и число подключений на
место игрока. Сервер ограничивает число комнат и удаляет простаивающие комнаты.

## Выбор стартовой руки и объявления

`static/presentation.css` оформляет три слоя поверх игрового поля: выбор стартовой
руки, временные объявления и итоговый экран. Разметка находится в `index.html`,
поведение — в `app.js`; дополнительных библиотек и изображений не требуется.

В начале матча игрок просматривает карты стрелками, клавишами ←/→ или миниатюрами.
Нажатие на центральную карту либо Enter отмечает её для замены. Можно отметить
до двух карт и отправить один существующий запрос `mulligan`. Пока второй игрок
не подтвердил руку, экран показывает ожидание. Правила обмена обрабатывает сервер.

Объявления хода, паса и исхода раунда строятся по изменениям подтверждённых снимков
`game`, а не по локальным кликам. Версия отсекает повторную доставку; первый снимок
при восстановлении страницы не воспроизводит историю уведомлений. Очередь сохраняет
порядок паса и итогов раунда, но заменяет устаревшие объявления хода. Анимация не
перехватывает мышь; настройка уменьшения движения отключает смещения.

После последнего объявления раунда открывается итог матча: победа, поражение или
ничья и таблица `history` с обеих сторон. Игрок сам возвращается к выбору колоды;
готовность соперника не закрывает его итоговый экран. Сдача во время выбора руки
тоже приводит к итогам. Эта презентация не меняет движок, протокол или хранение матчей.

При выборе лидера его карта увеличивается от позиции на столе к окну подтверждения.
Кнопки «Отмена» и Esc закрывают просмотр без команды серверу. Только «Применить»
отправляет существующее действие `leader`. Если версия матча изменилась, просмотр
закрывается; при потере связи применение блокируется. Описание берётся из каталога
для выбранного варианта лидера.

Для штандарта (`horn`) целями интерфейса являются только свободные `row-special`,
а не целые боевые ряды. Доступность каждого места определяется серверными `moves`.
«Военная академия» отображает в своём месте обычную иллюстрацию штандарта, но это
представление эффекта `leader_horn`: дополнительная карта в состоянии матча не создаётся.

Для анимации Казни сервер передаёт `game.scorched`: идентификаторы открытых карт,
уничтоженных последним подтверждённым действием. Список очищается на копии матча
перед следующим действием; правило работает также для Казни у отрядов и лидера.
Он не содержит карт руки или колоды и не заменяет текстовый журнал событий.

Браузер сохраняет только изображения этих карт на прежних местах, пока огонь
постепенно обрезает и затемняет их. Состояние матча уже обновлено сервером;
визуальные остатки недоступны для нажатия и не участвуют в счёте. Объявления
следующего хода и итоговый экран ждут завершения эффекта. Повторный снимок и
восстановление страницы не воспроизводят сгорание заново. В режиме уменьшения
движения используется короткое исчезновение без пламени и искр.

`static/scorch.js` рисует огонь на одном прозрачном Canvas над полем: мягкие
светящиеся частицы, дым, угли и тлеющую кромку. Контур каждой карты задаётся её
идентификатором и версией действия, одинаковыми для обоих игроков. Положение
берётся из текущего DOM, поэтому свои и чужие ряды и разные размеры окон
не требуют отдельных координат.

Время сгорания продвигается через `requestAnimationFrame`, а не по настенным
часам. В скрытой вкладке эффект приостанавливается и возобновляется после
`visibilitychange`; большой перерыв между кадрами не пропускает анимацию целиком.
Сервер не ждёт окончания огня и продолжает принимать допустимые действия.
`tests/browser_scorch.py` проверяет настоящие HTTP/WebSocket-сессии обоих игроков,
наличие рисунка на каждом Canvas и отдельно имитирует смену видимости вкладки.

## Показ карты соперника

Каждое успешное действие play записывает game.played: актор и снимок определения
уже сыгранной карты с её публичным идентификатором. До розыгрыша рука соперника
остаётся скрытой. Следующее действие очищает game.played; обновление присутствия сохраняет
ту же версию и не запускает показ повторно. Начальная загрузка и пропуск версий
показывают текущее поле сразу, без воспроизведения старого хода.

static/opponent-play.js отвечает за плавное появление крупной карты справа,
перемещение к реальному DOM-элементу ряда или отбоя и сгорание самой Казни.
До завершения показа frontend удерживает прежнее поле; дальнейшие снимки идут
в очередь по версиям, повторные сообщения одной версии объединяются. Проверка
ходов и состояние сервера продолжают работать независимо от анимации. Кнопки
действий зрителя временно недоступны. Новая карта скрыта в ряду до окончания
перемещения, затем показывается вместе с остальными результатами хода.

Анимации продвигаются по видимым кадрам и приостанавливаются в скрытой вкладке.
Выход из комнаты отменяет показ и очищает очередь, reduced-motion пропускает
крупный показ. Для огня крупной Казни используется отдельный экземпляр Canvas,
после чего запускается прежнее сгорание уничтоженных отрядов на поле.

## Фракционные данные

Фракция игрока определяется по выбранному лидеру из каталога. Сервер проверяет,
что стартовая колода состоит из отрядов этой фракции и общих карт. Нейтральность
погодных и особых карт записана в CardDefinition.faction. Отряды Сконе, её Шторм
и Мухомор доступны только Сконе; неколлекционные формы не попадают в стартовые колоды.
Начальная фракция передаётся в персональном состоянии комнаты через лидера,
а в состоянии матча явно присутствует players[].faction.

Пассивный «Натиск Империи» устанавливает leader_blocked при создании матча.
Пассивная «Северная стойкость» проверяет этот флаг при подсчёте силы под погодой.
Возврат Сконе запускается только при переходе к третьему раунду после очистки поля.
Оба случайных отряда каждой стороны извлекаются из отбоя до применения эффектов.
pending_actors хранит владельца каждого ожидающего выбора лекаря; round_resume_turn
возвращает обычный ход начинающему раунд после завершения всех таких выборов.
«Боевой клич» передаёт row в обычной команде leader, а усиление использует leader_horn.
Активные команды проверяют этот флаг независимо от состояния кнопки браузера.
Сведения «Шпионских игр» выдаются только в players[viewer].revealed; общие события
не содержат идентификаторов или имён вскрытых карт. Просмотр в браузере не меняет
состояние сервера. Список фильтруется по текущей руке соперника и очищается между
раундами. «Посмертная повинность» использует pending_levy и существующее действие
choose, но выбирает обычный отряд из чужого отбоя, без параметра линии.

Правила Широна проверяет tests/test_shiron.py, а tests/browser_shiron.py запускает
собственный тестовый сервер и две настоящие WebSocket-сессии для проверки всех
пяти способностей, конфиденциальности разведки и победы при равной силе.

## Развёртывание

Рабочая игровая часть запускается одной командой Python. Проверка `/healthz`
возвращает состояние процесса. Дальше вместе с владельцем проекта предстоит:

1. Разобрать и сохранить изменения в Git.
2. Выбрать способ фиксации зависимостей для воспроизводимой сборки.
3. Написать Dockerfile и объяснить каждый слой.
4. Описать локальный запуск через Compose.
5. Настроить CI для тестов и сборки, затем публикацию версионированного образа.
6. Настроить Linux-сервер, HTTPS, параметры окружения, журналирование и откат.

Для текущего хранилища в памяти используется один worker и одна реплика.
PostgreSQL/внешнее состояние и восстановление после перезапуска потребуют отдельного
изменения архитектуры, если появится такое требование.
