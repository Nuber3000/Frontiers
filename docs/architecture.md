# Устройство игровой версии

```text
Браузер (HTML / CSS / JavaScript)
  ├─ HTTP: каталог, создание комнаты, вход, готовность
  └─ WebSocket: команды игрока и персональные снимки состояния
        ↓
  app.py → rooms.py → engine.py
                       ├─ models.py — состояние матча
                       └─ catalog.py — определения карт и колод
```

## Файлы

| Файл | Ответственность |
| --- | --- |
| `models.py` | Описание карты, экземпляр с уникальным ID, карта на поле, состояние игрока |
| `catalog.py` | Авторская коллекция, пять лидеров, готовые колоды и проверка состава |
| `engine.py` | Допустимые действия, эффекты, пересчёт силы, раунды, персональный вид |
| `rooms.py` | Места игроков, комнаты, последовательная обработка, время хранения |
| `app.py` | HTTP/WebSocket, cookie, проверка входных данных и раздача интерфейса |
| `__main__.py` | Параметры локального запуска Uvicorn |
| `static/` | Браузерный интерфейс без внешних CDN и сборщика |
| `tests/test_engine.py` | Контракты правил и полные симулированные матчи |
| `tests/test_api.py` | Сессии, сетевой протокол и конкурентные команды |
| `tests/browser_smoke.py` | Два браузерных игрока, полный матч, возврат и реванш |

`cards.py`, `player.py` и два простых скрипта в `examples/` сохранены как первые
учебные примеры. Полноценный матч использует экземпляры карт из `models.py`:
каждая копия обладает собственным случайным ID, а выложенная карта — выбранным рядом.

## Атомарность действия

Команда включает ожидаемую `version`. Движок проверяет её, делает копию матча и
применяет действие к этой копии. Успех возвращает новое состояние с увеличенной
версией; ошибка оставляет исходное состояние нетронутым.

В комнате команды проходят через `asyncio.Lock`. Две команды с одной версией не
могут обе успешно изменить матч. Сервер проверяет очередь, наличие карты, ряд,
цель и доступность способности независимо от интерфейса.

Пример команды по WebSocket:

```json
{"type":"play","card_id":"случайный ID экземпляра","row":"ranged","version":7}
```

Ответ с обновлением:

```json
{"type":"state","state":{"code":"КОДКОМНАТЫ","me":0,"revision":12,"seats":[],"game":{}}}
```

Содержимое `game` в примере опущено. В настоящем ответе находятся игроки, поле,
счёт, погода, события и разрешённые действия. Игрок видит только свою руку и число
карт в чужой руке; порядок обеих колод не передаётся. Ошибка имеет тип `error` и
сообщение. При устаревшей команде ответ также содержит актуальный персональный снимок.

## Сессии и восстановление

Место игрока связано с HttpOnly cookie со случайным токеном. В памяти комнаты
хранится его SHA-256, а не исходный токен. Сам код приглашения позволяет занять
свободное место, но не читать чужой матч. Повторный вход с той же cookie возвращает
тот же слот. Токены не передаются в ссылке и не записываются в журналы игры.

Браузер восстанавливает WebSocket после сетевого разрыва и получает полный
снимок. Перезагрузка страницы использует сохранённый код комнаты и ту же cookie.
Сохранение состояния на диск пока отсутствует.

Запросы браузера с чужим Origin отклоняются; входные команды проверяются Pydantic.
WebSocket ограничивает размер сообщения, частоту команд и число подключений на
место игрока. Сервер ограничивает число комнат и удаляет простаивающие комнаты.

## Граница перед DevOps-этапом

Рабочая игровая часть запускается одной командой Python. Проверка `/healthz`
возвращает состояние процесса. Дальше вместе с владельцем проекта предстоит:

1. Разобрать и сохранить изменения в Git.
2. Выбрать способ фиксации зависимостей для воспроизводимой сборки.
3. Написать Dockerfile и объяснить каждый слой.
4. Описать локальный запуск через Compose.
5. Настроить CI для тестов и сборки, затем публикацию версионированного образа.
6. Настроить Linux-сервер, HTTPS, параметры окружения, журналирование и откат.

Для текущего хранилища в памяти используется один worker и одна реплика.
PostgreSQL/внешнее состояние и восстановление после перезапуска потребуют отдельного
изменения архитектуры, если появится такое требование.
